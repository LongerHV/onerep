# onerep v1 — Design

Date: 2026-09-23
Status: approved in brainstorming, pending spec review

## 1. Summary

onerep is a self-hosted, open-source gym progress tracker delivered as a PWA. It runs as a single Go binary backed by SQLite, serves server-rendered HTML (templ + htmx + Tailwind), authenticates users via OIDC, and exposes an MCP server so an AI assistant can analyse training history and draft new training plans.

Target deployment: one instance for a handful of users (owner, family, friends). Users are fully isolated from each other. A future SaaS redesign is possible but explicitly out of scope; the only concession to it is that all SQL lives behind a store layer.

## 2. Goals and non-goals

### v1 goals

- OIDC login, users auto-provisioned on first login.
- Exercise catalog (seeded + user-defined) and per-user equipment profiles.
- Training plans as schema-validated JSON documents with per-week templating, edited in a schema-aware JSON editor with a live resolved preview.
- Plan versioning; AI (via MCP) writes drafts that the user reviews as a diff and activates.
- Active plan with a cursor that determines the next workout.
- Companion mode: guided live workout with rest timer, RPE-based weight autoregulation, and offline-tolerant logging.
- Ad-hoc sessions outside any plan.
- History: session list and entry editor.
- Stats: e1RM over time per exercise, rep-max PR table + live PR badges, weekly hard sets per muscle group.
- MCP server with personal access token auth.

### Non-goals for v1 (deferred)

- Form-based plan editor.
- Automatic progression rules (the AI performs progression via MCP).
- Tonnage/volume charts, adherence stats, session calendar.
- Plan sharing, coach/athlete roles, public sign-up, horizontal scaling, Postgres.
- EMOM/AMRAP/time-capped circuits.
- Body weight, body measurements, calorie tracking.
- Full OAuth for MCP (needs an IdP supporting Dynamic Client Registration).
- Offline support outside companion mode.

## 4. Architecture

Single binary, organised by feature. Web handlers and MCP tools are thin adapters over the same services, so validation and business rules exist once.

```
cmd/onerep/            main, config, wiring, subcommands (serve, migrate, backup, recompute)
internal/
  auth/                OIDC flow, auth sessions, CSRF, API tokens, dev bypass
  exercise/            catalog, embedded seed data, equipment profiles, user exercise settings (TM)
  plan/                JSON Schema, validation, week expansion, versions/drafts, diff
  training/            sessions, sets, active plan cursor, sync endpoint logic
  calc/                e1RM, load resolution, plate/equipment rounding — pure, no I/O
  stats/               e1RM series, PR table, weekly muscle sets
  store/               SQLite repositories behind interfaces; schema.sql; migrations/
  web/                 chi routes, middleware, templ components, htmx handlers
  mcp/                 MCP tool and prompt definitions
web/static/            built CSS, companion JS, service worker, vendored JS libs
testdata/calc_cases.json  shared Go/JS calc test vectors
```

Dependency direction: `web`, `mcp` → services (`exercise`, `plan`, `training`, `stats`, `auth`) → `store`, `calc`. `calc` depends on nothing. Services depend on store interfaces, not concrete SQLite types.

## 5. Data model

Conventions: all IDs are UUIDv7 stored as TEXT. Session and set IDs are generated by the client so offline replays are idempotent. Weights are stored in kilograms (REAL). Timestamps are UTC (TEXT, RFC 3339 with milliseconds). Every user-owned table carries `user_id` and every query filters by it.

### Identity and setup

- `users`: `id`, `oidc_issuer`, `oidc_sub` (unique together), `email`, `name`, `unit` (`kg`|`lb`), `e1rm_window_days` (default 30), `created_at`.
- `auth_sessions`: `id` (random 256-bit, stored hashed), `user_id`, `csrf_token`, `expires_at`, `created_at`.
- `api_tokens`: `id`, `user_id`, `name`, `token_hash`, `scope` (`mcp`), `last_used_at`, `created_at`, `revoked_at`.
- `equipment`: `id`, `user_id`, `name`, `kind` (`barbell`|`dumbbell`|`machine`|`cable`|`bodyweight`), `unit`, `config` JSON:
  - barbell: `{ "bar": 20, "plates": [25, 20, 15, 10, 5, 2.5, 1.25], "plate_pairs": {"1.25": 2} }` (plate list = available sizes; optional per-size pair counts, unlimited if absent)
  - dumbbell: `{ "weights": [2, 4, 6, ...] }`
  - machine / cable: `{ "stack": [5, 10, 15, ...] }` or `{ "min": 5, "step": 5, "max": 100 }`
  - bodyweight: `{}`
- `exercises`: `id`, `user_id` (NULL = global seed), `slug`, `name`, `measurement` (`weight_reps`|`bw_reps`|`reps`|`time`|`distance_time`), `equipment_kind`, `primary_muscles` JSON array, `secondary_muscles` JSON array, `aliases` JSON array. Unique `(user_id, slug)`. A user row with the same slug as a global row shadows it for that user.
- `exercise_alternatives`: `user_id`, `slug`, `alt_slug`. Default alternatives come from seed data; user rows add to them.
- `user_exercise`: `user_id`, `slug`, `equipment_id` (nullable), `training_max_kg` (nullable), `updated_at`.
- `training_max_log`: `id`, `user_id`, `slug`, `old_kg`, `new_kg`, `source` (`web`|`mcp`), `note`, `created_at`.

### Plans

- `plans`: `id`, `user_id`, `name`, `archived`, `created_at`.
- `plan_versions`: `id`, `plan_id`, `version` (int, increasing per plan), `doc` JSON (authored form), `status` (`draft`|`active`|`superseded`), `source` (`web`|`mcp`), `note`, `created_at`. At most one `active` row per plan (partial unique index).
- `active_plan`: `user_id` (PK), `plan_id`, `cursor_week` (1-based), `cursor_day` (0-based index into days applicable to that week).

### Training log

- `sessions`: `id`, `user_id`, `plan_version_id` (NULL = ad-hoc), `week`, `day`, `snapshot` JSON (resolved prescription at start), `started_at`, `finished_at`, `notes`, `updated_at`.
- `sets`: `id`, `session_id`, `slug` (exercise actually performed), `group_pos`, `set_pos`, `kind` (`warmup`|`working`|`drop`|`amrap`), `prescribed` JSON (nullable for ad-hoc), `weight_kg`, `reps`, `rpe`, `duration_s`, `distance_m`, `e1rm_kg` (derived cache), `done_at`, `updated_at`, `deleted_at`.
- `applied_ops`: `op_id` (PK), `user_id`, `applied_at`, `result` — idempotency record for sync.

Derived data rules:
- `e1rm_kg` is recomputed on every set write. `onerep recompute` rebuilds all derived values after formula changes.
- For `bw_reps`, `weight_kg` holds the added load; e1RM is not computed in v1 (no body weight tracking).
- Deletes are soft (`deleted_at`) so a late offline upsert cannot resurrect a deleted set.
- Stats are SQL queries over `sets`; no aggregate tables in v1.

## 6. Plan document

### Format

```json
{
  "name": "Upper/Lower RPE block",
  "unit": "kg",
  "weeks": 4,
  "days": [
    {
      "name": "Upper A",
      "groups": [
        { "rest_s": 180, "exercises": [
          { "slug": "barbell-bench-press",
            "alternatives": ["dumbbell-bench-press"],
            "notes": "pause first rep",
            "sets": [
              { "kind": "warmup", "count": 2, "reps": 5, "load": {"pct_tm": 0.5} },
              { "count": [3,3,4,2], "reps": 5, "load": {"rpe": [7,8,9,6]} },
              { "kind": "drop", "count": 1, "reps": 10, "load": {"drop_pct": 0.2} }
            ]}]},
        { "rest_s": 90, "exercises": [
          { "slug": "pull-up", "sets": [{ "count": 3, "reps": "6-10", "load": {"rpe": 8} }] },
          { "slug": "cable-lateral-raise", "sets": [{ "count": 3, "reps": 15, "load": {"weight": 7.5} }] }
        ]}
      ]
    },
    { "name": "Deload extra", "only_weeks": [4], "groups": [] }
  ]
}
```

### Rules

- `weeks` ≥ 1. `unit` defaults to the user's unit.
- Per-week templating: any numeric scalar in `count`, `reps`, `duration_s`, `rest_s`, and `load` values may instead be an array of exactly `weeks` elements. Element *i* applies to week *i+1*. `null` in a `count` array means the set line is omitted that week.
- `only_weeks` on a day restricts it to the listed weeks.
- `reps`: integer, range string `"lo-hi"`, or `"AMRAP"`. Time-based exercises use `duration_s` instead of `reps`.
- `kind` defaults to `working`.
- `load` is exactly one of: `weight` (absolute, plan unit), `pct_tm` (fraction of training max), `rpe` (target RPE, 6–10 in 0.5 steps), `drop_pct` (fraction below the previous set's actual weight). `load` may be omitted for bodyweight/reps/time exercises.
- `rpe` may also appear alongside `weight`/`pct_tm` as an informational target.
- A group with more than one exercise is a superset: companion mode alternates A1 → B1 → A2 → B2…; `rest_s` applies after each complete round. Exercises with differing set counts drop out of the rotation when exhausted. A group of one is a normal straight-set block and `rest_s` applies between its sets.
- `alternatives` augments the catalog alternatives for that slot.

### Validation

Three layers, run identically for web saves and MCP drafts:
1. JSON Schema (embedded, published at `/schema/plan.json` and via MCP `get_plan_schema`).
2. Semantic checks: slugs exist for the user; per-week arrays have length `weeks`; `only_weeks` within range; range strings valid; `drop_pct` not on the first set of an exercise; at least one day applies to each week.
3. Result: list of `{ pointer, message }` (JSON Pointer into the document). Drafts may be saved with warnings but not with errors.

### Resolution

Two pure steps:

1. **Expand(doc, week, day)** → ordered list of groups of concrete prescribed sets (per-week values selected, `count` expanded, units normalised to kg).
2. **ResolveLoads(sets, ctx)** where `ctx` = per-exercise TM, current e1RM, equipment profile:
   - `weight` → as given.
   - `pct_tm` → `pct × TM`; if no TM, unresolved.
   - `rpe` → `e1RM × pct(reps, rpe)` from the RTS table, where e1RM is the best `e1rm_kg` for that slug within `e1rm_window_days`; if none, unresolved. Ranges use the lower bound for the lookup.
   - `drop_pct` → resolved at run time from the previous set's actual weight.
   - Result rounded down to the nearest achievable load for the linked equipment (barbell: bar + symmetric plate pairs; dumbbell/stack: nearest lower available value). Unlinked exercises round to 0.5 kg / 1 lb.
   - Unresolved sets display "pick weight"; the user enters the load.

When a session starts, the expanded and resolved day is written to `sessions.snapshot`. During the session the client re-runs ResolveLoads for remaining RPE-targeted sets of the current exercise after each logged set, using the e1RM of the last completed working set (see §7).

Plan preview in the editor shows every week × day expanded with resolved loads.

## 7. Calculations (`calc`)

- **RTS table:** percentage of 1RM for reps 1–12 × RPE 6–10 in 0.5 steps (Tuchscherer). Embedded as a constant table.
- **e1RM for a set:**
  - with RPE ≥ 6 and reps ≤ 12: `weight / pct(reps, rpe)`;
  - otherwise with reps ≤ 12: Epley `weight × (1 + reps/30)` (reps = 1 → weight);
  - reps > 12 or no weight: none.
  - Stored alongside a `method` distinction for charting: RPE-based vs rep-based (derivable from whether `rpe` is set; no extra column).
- **In-session adjustment:** after a working set at an RPE-targeted slot, the session e1RM for that slug = the e1RM of the last completed working set. Remaining RPE-targeted sets are re-resolved from it.
- **Rounding:** as in §6.
- **Shared test vectors:** `testdata/calc_cases.json` holds input → expected output cases for e1RM, RTS lookups, load resolution, and rounding. The Go tests and the JS tests (`node --test`) both consume it; CI fails if either diverges.

## 8. Active plan and cursor

- Each user has at most one active plan (`active_plan`). Activating a plan sets the cursor to week 1, day 0.
- "Next workout" = cursor position. Starting it creates a session for (week, day). Finishing it advances the cursor to the next applicable day; after the last day of a week, to day 0 of the next week.
- Past the final week the plan is "complete": the home screen offers to restart it or ask the AI for the next block. Restarting resets the cursor.
- The user can skip the current day (advance without a session) or start any (week, day) manually; starting a manual day moves the cursor to it.
- Activating a new version of the already-active plan keeps the cursor if the (week, day) still exists in the new version, otherwise resets it to week 1, day 0 and warns in the UI.
- Ad-hoc sessions (`plan_version_id` NULL) never move the cursor; the user adds exercises by slug during the session.

## 9. Companion mode and offline sync

### Starting

`POST /sessions` (plan day or ad-hoc) creates the session server-side, stores the snapshot, and redirects to `/sessions/{id}/live`. The page embeds a JSON bootstrap: snapshot, per-slug TM/e1RM/equipment, per-slug PR table, last performance per slug, and the alternatives list with their context. From then on the page functions without network.

### Client

- Vanilla JS module with Alpine for reactive rendering.
- IndexedDB stores: session bootstrap, local set state, outbox.
- Outbox ops: `upsert_set`, `delete_set`, `swap_exercise`, `edit_notes`, `finish_session`. Each op has a client-generated `op_id` (UUIDv7) and `client_ts`.
- UI: one focused card per set showing exercise, target (reps / load / RPE), last time's result, pre-filled inputs, and actions Done / Skip / Swap / Add set. Superset groups rotate as in §6. A session overview lists every set; tapping a logged set opens it for edit or delete.
- After Done: recompute remaining RPE targets (§7), check PR against bootstrap PR table (badge is advisory; server is authoritative), start rest timer.
- Rest timer: stores `rest_end` timestamp in IndexedDB; display derived from `rest_end - now`. Wake Lock API held while the live page is visible. On expiry: vibrate + short audio cue. Correct after screen lock or reload.
- A small indicator shows unsynced op count and a "re-login needed" state.

### Sync endpoint

- `POST /api/sync` with body `{ "ops": [{ "op_id", "op", "payload", "client_ts" }] }`.
- Server applies ops in order, each in its own transaction, recording `op_id` in `applied_ops`. An already-applied `op_id` returns its stored result without reapplying.
- Set upserts use last-write-wins on `updated_at` (client-supplied, clamped to server time + 5 min). An upsert for a set with `deleted_at` set is ignored.
- Response: per-op `{ op_id, status: "applied"|"duplicate"|"rejected", reason? }`. Rejected ops are moved to a local "failed" list visible in the UI, never silently dropped.
- Flush triggers: after each enqueued op, on the `online` event, and every 30 s while ops remain.
- Auth: the normal session cookie + CSRF header. On 401 the client keeps the outbox, shows "re-login needed"; after re-login the live page resumes syncing.
- `finish_session` sets `finished_at` and advances the cursor (§8).

### Service worker

Caches the app shell, CSS, companion JS, and vendored libs (cache-first, versioned by build hash). `/sessions/{id}/live` is served network-first with cache fallback so an open session can be reopened offline. All other navigations are network-only with an offline fallback page.

### History editing

After a session, edits happen on normal htmx pages (`/history`, `/history/{session}`) that call the same `training` service used by sync. Users can edit/delete/add sets, edit notes and times, or delete a whole session.

## 10. Plan editor, versions, and diffs

- `/plans/{id}/edit`: `vanilla-jsoneditor` (text + tree modes) loaded with the plan JSON Schema; beside it an htmx-refreshed preview (debounced `POST /plans/preview`) showing validation errors and the resolved week × day tables.
- Saving from the web creates a new version. The user chooses "save as draft" or "save and activate".
- MCP `save_plan_draft` always creates `draft` versions. Updating an existing draft from MCP replaces that draft row's `doc` (drafts are mutable; active/superseded versions are immutable).
- `/plans/{id}/versions/{v}/diff`: side-by-side JSON diff against the active version plus a resolved diff per week × day (sets added/removed/changed). Actions: Activate, Discard.
- Activating supersedes the previous active version (§8 for cursor behaviour).

## 11. Authentication

- OIDC authorization code flow with PKCE. Callback upserts the user by `(issuer, sub)` and refreshes `email`/`name`.
- Auth session: random ID in an HttpOnly, Secure (except dev), SameSite=Lax cookie; 30-day sliding expiry; stored hashed in `auth_sessions`.
- CSRF: per-session token, sent by htmx via `hx-headers` and by the companion client as `X-CSRF-Token`; required on all non-GET requests except `/mcp` (bearer-token auth).
- Dev bypass: `ONEREP_DEV_USER=<name>` logs in as that user without OIDC; honoured only when `ONEREP_ENV=dev`; logs a warning at startup.
- Local Dex: `dev/dex.yaml` configures a static password connector with two users (`alice`, `bob`) and an `onerep` client. Run with the `dex` binary from the Nix dev shell (`task dev:dex`). `deploy/compose.yaml` shows a production-like app + Dex setup.
- API tokens for MCP: created/revoked at `/settings/tokens`; shown once; stored as SHA-256 hash; sent as `Authorization: Bearer <token>`.

## 12. MCP server

Mounted at `/mcp` (Streamable HTTP) using `modelcontextprotocol/go-sdk`, authenticated by API token. All tools act as the token's user.

| Tool | Behaviour |
|---|---|
| `list_exercises` | Search catalog by slug, name, alias, or muscle. |
| `create_exercise` | Create a user exercise (slug, name, measurement, equipment kind, muscles, aliases). |
| `get_plan_schema` | Plan JSON Schema plus a prose description of the format and rules. |
| `get_plan` | Active version (default) or a specific version: authored JSON + resolved preview for all weeks. |
| `list_plans` | Plans with versions and statuses. |
| `validate_plan` | Validate a document without saving; returns errors/warnings. |
| `save_plan_draft` | Create a draft (new plan or new version of an existing plan) or update an existing draft; returns version ID and diff page URL. |
| `list_sessions` | Sessions filtered by date range and/or exercise, with summary. |
| `get_session` | Full session: snapshot (prescribed) vs sets (actual). |
| `get_exercise_stats` | e1RM series, PR table, recent best sets, current TM for a slug. |
| `get_weekly_muscle_volume` | Hard sets per muscle per ISO week for a date range. |
| `set_training_max` | Update a TM; writes `training_max_log` with `source=mcp`. |

MCP prompts: `review_block` (analyse the latest completed block and propose the next as a draft) and `build_plan` (gather goals, schedule, and equipment, then draft a plan).

The AI cannot modify logged sessions or sets, and cannot activate plans.

## 13. Stats

- **Exercise page** `/exercises/{slug}`: uPlot line chart of session-best e1RM over time, RPE-based and rep-based points styled distinctly; PR table of best weight for each rep count 1–12 with date and session link; current TM with edit.
- **PR detection:** a set is a PR when its weight exceeds the previous best for that exact rep count and slug (working/amrap sets only). Server computes on write; companion shows an advisory badge from the bootstrap table.
- **Muscles page** `/stats/muscles`: weekly hard sets per muscle for the last 12 ISO weeks (table + stacked bar chart). A hard set is a non-deleted `working`, `drop`, or `amrap` set with `rpe` ≥ 7 or no RPE recorded. Primary muscle counts 1.0, each secondary 0.5.
- Chart data is served as JSON from `/api/stats/...`, same-origin, cookie auth.

## 14. Exercise catalog seed

- Embedded file `internal/exercise/seed/exercises.json`: 100–150 common exercises with slug, name, measurement, equipment kind, primary/secondary muscles, aliases, and default alternatives.
- Muscle vocabulary (fixed enum): chest, front-delts, side-delts, rear-delts, lats, upper-back, traps, biceps, triceps, forearms, abs, obliques, lower-back, glutes, quads, hamstrings, adductors, abductors, calves, neck.
- Seed is loaded into `exercises` (user_id NULL) at startup, upserting by slug; seeded slugs are never removed, only marked hidden if dropped from the file.

## 15. Operations

- Config via env: `ONEREP_DB` (default `./onerep.db`), `ONEREP_LISTEN` (default `:8080`), `ONEREP_BASE_URL`, `ONEREP_OIDC_ISSUER`, `ONEREP_OIDC_CLIENT_ID`, `ONEREP_OIDC_CLIENT_SECRET`, `ONEREP_ENV` (`prod`|`dev`), `ONEREP_DEV_USER`.
- SQLite pragmas: `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=NORMAL`. One write connection (`SetMaxOpenConns(1)` on a dedicated handle) and a separate read pool.
- Migrations: edit `internal/store/schema.sql`; `task migrate:diff NAME=...` runs `atlas migrate diff` against `sqlite://dev?mode=memory` with `--dir-format golang-migrate` into `internal/store/migrations/`. Migrations are embedded and applied at `serve` startup (disable with `ONEREP_AUTO_MIGRATE=false`) or via `onerep migrate`.
- Subcommands: `serve`, `migrate`, `backup <path>` (`VACUUM INTO`), `recompute`.
- Observability: `log/slog` JSON logs with request IDs; `/healthz` (DB ping).
- Build: `task build` runs `templ generate`, Tailwind build, `go build`. `task image` runs `ko build` (distroless static base). README documents Litestream for continuous backup.
- Development: `nix develop` provides go, gopls, gotools, golangci-lint, templ, air, tailwindcss v4, node 24, sqlite, atlas, ko, go-task, dex. `task dev` runs air + templ watch + tailwind watch with `ONEREP_DEV_USER` set.

## 16. Error handling

- Validation errors (plan, forms, MCP args) → structured `{ pointer, message }` lists; htmx renders them inline; MCP returns them as tool errors with the list.
- Unexpected errors → logged with request ID; htmx receives an error fragment shown as a toast containing the request ID; JSON endpoints return `{ "error", "request_id" }`.
- Authorisation: any access to another user's resource returns 404 (not 403) to avoid leaking existence.
- Sync rejections as in §9.

## 17. Testing

- `calc`: table-driven Go tests; shared vectors in `testdata/calc_cases.json` run by both Go and `node --test` for the JS module.
- `plan`: golden tests — authored documents expanded for every week/day compared to `testdata/*.golden.json`; validator tests for each semantic rule.
- Services + store: tests against a real temporary SQLite database with migrations applied; no DB mocks.
- Sync: idempotent replay, out-of-order ops, delete-then-late-upsert, rejected op reporting, cursor advance on finish.
- Auth: middleware tests for cookie sessions, CSRF, bearer tokens, dev bypass gating.
- MCP: in-process client tests via the go-sdk covering each tool including user isolation.
- Web: handler tests with `httptest` for key pages and htmx fragments.
- E2E (optional in v1, may lag): one Playwright test for companion mode including going offline mid-session.
- CI: `go test ./...`, `golangci-lint`, `node --test`, `templ generate` + `git diff --exit-code`, `atlas migrate validate`.
